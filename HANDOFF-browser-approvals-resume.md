## In progress: decision 1 (resume) — design and what exists
Design: the turn still ends when it parks at an approval. After the person answers, the **frontend** starts a "resume" turn (no new user message) over the existing SSE route; the model sees the settled tool results and continues. The server can't push into the chat, so it has to be frontend-initiated.

Server edits already in the working tree (committed as a WIP commit; **untested** — only `ast.parse` checked):
- `conversation/orchestrator/pipeline.py`: `TurnRequest.resume: bool`; `run_turn` delegates to new `_resume_turn` (requires last message to be a tool result else `Failed(code="nothing_to_resume")`; sets `request.text` to the last user text so personality/memory/verification read the original ask; no `ASSISTANT_INPUT` event, no pushed user message; yields `Routed(Intent.MULTI_STEP…)` then `_run_model_loop`).
- `server/jarvis/routes/approvals.py`: `_can_carry_on()` (active chat, no other pending approvals, tail is a tool message), `_settle_refusal()` (deny/cancel/timeout now settle the parked tool result to an error "The person said no…"/"timed out…" — previously only allow settled), `resumable` flag in the decide response.
- `server/jarvis/routes/turn.py`: `GET /api/chat/stream?resume=<approvalId>` → `_resume_stream` (404 if approval not in this chat, 409 if something still pending or nothing to resume).
- `conversation/prompt.py`: `answered_approvals_section` now words a `timeout` status correctly (did NOT run).
